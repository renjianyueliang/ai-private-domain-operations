# 公开开源后的增长与申请证据计划

目标不是制造虚假热度，而是形成可核验的维护、使用和生态价值证据。任何项目资格申请都应使用真实数据。

## 公开后 30 天

- 发布 `v0.1.0`，提供清晰安装说明和已知边界。
- 邀请 3–5 位目标用户独立安装，记录成功率、首次跑通时间和阻塞点。
- 将反馈转成公开 Issue，并至少完成一轮带验证记录的修复。
- 每周维护一次路线图/变更记录，公开说明取舍。

## 30–60 天

- 争取至少 2 位非维护者提交可合并的 Issue、文档或代码贡献。
- 发布一个脱敏的端到端演示和一篇技术/产品复盘。
- 统计 GitHub traffic、独立安装反馈、活跃 Issue/PR、版本下载与真实使用案例。
- 与相邻开源项目建立可解释的集成或互操作场景，而不是只交换 Star。

## 申请材料应回答

1. 项目为哪类用户解决什么具体问题，为什么现有工具不足。
2. 申请人是否是核心维护者，并能否证明持续维护权限和记录。
3. 公开仓库的实际使用量、贡献者、发布节奏和生态依赖是什么。
4. 资源将用于哪些明确维护任务，完成后如何公开回馈社区。

## 证据台账

每月记录以下真实数据，不达标就如实写“暂无”：

- Stars、Forks、Watchers 和独立贡献者数。
- 版本下载量、独立安装成功数、活跃部署或试用团队数。
- 30 天内合并的 PR、关闭的 Issue、响应时间和发布次数。
- 可公开引用的案例、文章、演示、集成和社区讨论链接。

不得购买 Star、伪造下载量、虚构客户或把自动账号当成真实社区参与。评审更看重可信、持续且与生态相关的证据。
