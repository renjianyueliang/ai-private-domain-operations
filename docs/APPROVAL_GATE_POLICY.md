# 批准与风险门策略

| 风险级别 | 例子 | 当前是否可自动执行 |
|---|---|---|
| `read_only` | 查状态、读代码、运行无副作用检查、形成报告 | 是，单次最多一个 |
| `low_risk_write` | 项目内文档、小测试、明确允许路径的小修复 | 是；仅限 linked worktree、固定验证和人工审查 |
| `controlled_write` | 认证、权限、数据库结构、依赖、较大业务逻辑 | 必须逐次人工批准 |
| `high_risk` | 部署、真实渠道、密钥、支付、客户数据、批量触达、删除 | 必须逐次批准且关键动作人工执行 |

## 永久门控动作

以下动作即使任务写成 `auto_runnable` 也必须拒绝：部署/发布、合并主分支、真实账号登录、修改凭据、采购/付费、真实客户触达、调用真实运营接口、删除或迁移业务数据、绕过平台限制。

## 停止条件

- 队列 JSON 无效、任务 ID 重复、依赖不存在或循环。
- 工作区存在与任务允许路径重叠的未知改动。
- 当前分支为 `main`，或者目标路径超出仓库。
- 测试失败、结果不确定、需要新增依赖或外部账号。
- 任务描述与允许路径/风险级别不一致。

遇到停止条件只报告证据和下一步，不自行绕过。

## 阶段 3 独立门

- 主工作区与 `main`/`master` 分支拒绝低风险自动写入。
- 删除、重命名、超过 20 个文件、超出 `allowed_paths` 均拒绝。
- `AGENTS.md`、`TASK_QUEUE.json`、`STATUS.md`、批准策略和自动化配置属于控制面，自动任务不得修改。
- 队列中的 `acceptance_tests` 不直接执行；只允许代码内固定的 `verification_profile`。
- 自动任务的终点是待人工审查的 worktree 差异和验证报告。

## 阶段 4 持续交付门

- 只有 `low_risk_write` 且固定验证成功的任务可以自动完成和提交。
- `Complete-AITeamTask.ps1` 只能将当前任务从 `ready` 改为 `done`、关闭 `auto_runnable` 并追加证据。
- `Test-AITeamDeliverySet.ps1` 必须确认策略和其他任务未改变，才允许提交。
- 只允许普通 push 到 `codex/ai-team-operating-system` 并更新既有草稿 PR #2；禁止 force push、自动合并和部署。
- `controlled_write` 与 `high_risk` 不因持续开发而降级，仍然需要逐次人工批准。
