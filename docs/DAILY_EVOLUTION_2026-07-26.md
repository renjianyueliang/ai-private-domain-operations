# 每日自动进化：获客到人工接管的闭环验收契约

日期：2026-07-26
项目：规划全自动 AI 私域员工
本轮类型：产品规格与验收标准（不接真实渠道、不发送消息）

## 今日只推进的一个演进点

把现有“AI 获客舱、私信聚合中心、线索 CRM”从三个相邻原型，收敛为一条可验证、可审计的最小闭环：

> 获客战役产生来源内容 → 客户主动咨询 → AI 生成建议 → 风险规则决定是否必须人工 → 人工确认或接管 → 线索进入明确的下一步。

本轮不实现后端状态变更，只冻结下一步实现必须满足的用户路径、状态转换、审计证据和验收口径。

## 为什么优先做这一步

- `AcquisitionCockpit` 已展示战役、阶段、员工任务和预计线索，但线索还不能追溯到具体战役。
- `UnifiedInbox` 已展示风险、AI 建议和三个处理动作，但按钮尚未形成持久化结果或审计记录。
- 线索 CRM 已展示阶段与下一步，但尚未证明一次人工处理会同步更新会话和线索。
- 如果先继续扩展页面，后续接 API 时容易出现“界面显示已处理、后台仍未处理”的信任风险。

## 核心用户与成功结果

主要用户：每天处理获客和私信的运营员工。
协作用户：负责高风险审批的合规员工，以及最终承接商机的销售/顾问。

用户成功结果：运营员工在一个工作回合内，能回答以下四个问题，并完成一个安全动作：

1. 这条咨询来自哪个战役和哪条内容？
2. 为什么它可以发送，或为什么必须转人工？
3. 当前由谁负责、最迟何时处理？
4. 处理后，线索下一步是什么，系统留下了什么证据？

## 最小用户路径

1. 用户从“AI 获客舱”打开某个战役，查看正在运行的内容与私域承接目标。
2. 用户进入“私信聚合中心”，看到由该战役产生的会话，并能识别来源战役、来源内容和平台。
3. 系统展示 AI 回复建议、风险等级、命中的规则和建议责任人。
4. 低/中风险会话允许“确认发送”或“加入跟进”；高风险会话禁用发送，只允许“转人工”。
5. 动作成功后，会话状态、负责人、线索阶段和下一步同步更新，并出现明确的成功反馈。
6. 用户在“线索 CRM”中找到同一条线索，看到刚刚的处理结果和待办时限。

## 状态与动作契约

| 当前状态 | 可用动作 | 成功后的状态 | 必须记录的证据 | 禁止行为 |
| --- | --- | --- | --- | --- |
| `ai_drafting` | 等待草稿、转人工 | `ready_to_send` 或 `human_required` | 模型/规则版本、生成时间、命中规则 | 草稿未完成时发送 |
| `ready_to_send` | 确认发送、转人工、加入跟进 | `follow_up` 或 `human_required` | 操作者、确认时间、最终文案、渠道 | 未经确认自动发送 |
| `human_required` | 转人工 | `follow_up` | 原因、接管人、接管时间、SLA | 启用“确认发送” |
| `follow_up` | 更新下一步、关闭 | `follow_up` 或 `closed` | 新阶段、下一步、负责人、时间 | 无下一步直接标记完成 |
| `closed` | 查看记录 | `closed` | 关闭原因、最终结果 | 静默重新打开或再次发送 |

## 数据关联最小要求

每条进入聚合中心的会话至少包含：

- `tenantId`：保证租户隔离。
- `campaignId`：追溯到获客战役。
- `sourceContentId` 与 `sourceContentTitle`：追溯到具体内容。
- `platform` 与外部消息占位标识：区分渠道；本地演示不得伪装为真实外部消息 ID。
- `risk`、`matchedRules`、`status`：解释分流依据。
- `owner`、`nextAction`、`dueAt`：形成可执行待办。
- `auditEvents`：记录状态变化，不覆盖历史。

## 验收场景

### 场景 A：中风险咨询由运营确认

- 给定一条 `ready_to_send` 的中风险会话。
- 当运营员工确认安全版本时，系统必须先展示最终文案和渠道。
- 确认后，会话进入 `follow_up`，显示成功反馈，并在 CRM 生成下一步。
- 刷新页面后结果仍存在；同一动作重复提交不得产生两次记录。

### 场景 B：高风险咨询强制人工接管

- 给定一条 `human_required` 的高风险会话。
- “确认发送”必须不可用，并以文字说明命中的规则，不能只靠颜色或图标。
- 点击“转人工”后必须指定或确认接管角色、处理时限和下一步。
- 会话与 CRM 同步显示接管人；不得调用真实发送接口。

### 场景 C：从线索反查来源

- 从 CRM 打开线索后，用户可回到对应会话。
- 会话中可查看来源战役和来源内容。
- 战役指标只统计可追溯线索，演示数据必须持续标注为样例。

### 场景 D：失败与并发

- 保存失败时保留用户输入并给出可重试提示，不能显示为已处理。
- 两名员工同时处理同一会话时，后提交者收到“状态已变化”的提示。
- 没有 `campaignId` 的历史会话可显示“来源未知”，但不能归因到任意战役。

## 完成定义

- 上述 A-D 场景均有自动化或可重复的本地测试步骤。
- 高风险会话不存在绕过人工确认的客户端或服务端路径。
- 会话、线索和审计记录在一次动作后保持一致。
- 关键状态不只依赖颜色，键盘可完成选择与确认；焦点和成功/失败提示可感知。
- 所有数据均为本地 mock 或测试数据，不使用真实客户资料，不触达真实平台。

## 本轮边界

- 不部署、不发布、不推送、不创建 PR。
- 不登录或授权任何渠道账号，不调用真实消息、CRM、支付或运营接口。
- 不修改当前正在开发的获客舱、统一收件箱、主工作台和样式文件。
- 不新增依赖，不启动长期服务，不把“预计线索”解释为真实获客结果。

## 下一步实现拆分（后续每次仍只取一个）

1. 先为会话模型增加 `campaignId`、来源内容和只追加的审计事件，并补纯函数状态转换测试。
2. 再让“转人工”在本地存储中持久化负责人、SLA 和下一步。
3. 最后实现“确认发送”的本地模拟确认页；真实渠道调用继续保持禁用。
